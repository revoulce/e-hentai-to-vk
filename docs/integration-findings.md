## Обновление: адаптер VK

В живой проверке `wall.getById` для `-217669377_12062` вернул только `donut.is_donut` и `can_publish_free_copy`; `paid_duration` отсутствует при обоих значениях `extended`. Владелец подтвердил постоянный режим этой конкретной записи. Добавлено подтверждение с точным ID в `VK_DONUT_PERMANENT_CONFIRMED_POST`, применяемое только при отсутствующем поле; явно конечный срок по-прежнему блокируется. Официальная страница [wall.post](https://dev.vk.com/ru/method/wall.post) подтверждает значение `-1` для постоянного Donut. Публикация и сверка теперь корректно принимают отсутствие необязательного срока при проверке результата сохранённого запроса с `donut_paid_duration=-1`.

После исправления `npm run check` прошёл: 47 тестов сервера, 17 unit-тестов и 8 UI-тестов расширения; обе сборки и обновлённая Compose-конфигурация проверены. Живой `vk:check` подтвердил группу, права и Donut с `durationSource: owner_confirmation`; оставшееся состояние — `privacy_verification_required`, поскольку проверка закрытости фотографий ещё не подтверждена. Новые записи в VK не создавались.

Затем владелец подтвердил, что уже проверял недоступность закрытого поста и фотографий для обычного подписчика. В локальной `.env` сохранено `VK_PHOTO_PRIVACY_VERIFIED=true`. Повторная проверка прав, группы, Donut и адреса загрузки завершилась с `state: ready` и кодом выхода 0. Приватность подтверждена владельцем; проверка сервера была только читающей, новые публикации не создавались.

Добавлен настоящий адаптер API 5.199 для `quetzalcoatl_cosplay`: проверка пользовательских прав и администратора, фото стены, 4/9 вложений, публикация от имени сообщества, стабильный `guid`, `donut_paid_duration=-1`, чтение результата и сверка неизвестной операции. Проверка `-1` опирается на существующий пост этой группы, вручную настроенный навсегда: `paid_duration` читается из VK до запуска обычного поста. Приватность вложений остаётся отдельным обязательным условием готовности. Цель очереди фиксируется в SQLite миграцией `003_vk_target.sql`.

Состояние и причины блокировки показаны в расширении. Добавлены защищённый `POST /vk/check`, команды `vk:auth`/`vk:check`, `.env.example` и дополнение Docker Compose. Порядок настройки — [vk.md](vk.md). Новые автоматизированные проверки используют фиктивные ответы VK; пользовательский токен ещё не предоставлен, реальные записи не публиковались. ## Проверенная основа

Из npm registry получены и закреплены Fastify 5.12.5, sharp 0.35.5, Zod 4.6.5, TypeScript 7.0.2, tsx 4.23.15. Node.js 24.21.0 выбран для целевого запуска и Docker. SQLite используется через встроенный `node:sqlite`, без отдельной БД и брокера.

Проверка исходной версии: 24 теста прошли на локальной Node.js 26.6.0 и отдельно на целевой Node.js 24.21.0. Дополнительно добавлены проверки преобразования статических WebP/GIF/AVIF, ориентации, исходного и итогового SHA-256, дубликатов, квоты при увеличении файла и хранения обеих копий после перезапуска. GIF/WebP с двумя кадрами, APNG и AVIF с брендом последовательности `avis` отвергаются. Проверка SQLite backup/restore восстанавливает принятую очередь, настройки и файлы. `docker compose ... config --quiet` завершён успешно; контейнер не собирался из-за неработающего Docker daemon. На Ubuntu эти проверки пока не выполнялись.

В [документации Node 24.21.0](https://github.com/nodejs/node/blob/v24.21.0/doc/api/sqlite.md) `node:sqlite` имеет статус Release candidate (Stability 1.2), поэтому версия runtime закреплена и доступ к БД изолирован.

Потоковая загрузка реализована через [официальный API content type parser Fastify](https://fastify.dev/docs/latest/Reference/ContentTypeParser/); собственный счётчик проверяет реальное число байтов, поскольку при возврате сырого потока стандартное накопление тела не используется. Ограничение декодирования и отказ при повреждённых данных задаются по [документации sharp](https://sharp.pixelplumbing.com/api-constructor/). JPEG/PNG проходят полное декодирование и сохраняются без изменения байтов. Статические WebP/GIF/AVIF преобразуются в PNG с учётом ориентации до предпросмотра; исходник и результат учитываются в квоте и сохраняются. Число кадров проверяется по [метаданным sharp](https://sharp.pixelplumbing.com/api-input/); дополнительно проверяются PNG `acTL` и AVIF `avis`, определённый в [спецификации AVIF](https://aomediacodec.github.io/av1-avif/#avif-image-sequence-brands).

В [официальной схеме VK wall](https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json) есть `donut_paid_duration` и пользовательский тип токена. Наличие параметра **не подтверждает** значение постоянного платного режима, применимость авторизации к конкретному приложению или приватность сохранённых фотографий. Эти свойства требуют отдельно согласованных живых проверок из раздела 8 ТЗ.

## Реализованный этап

Серверное ядро включает API всех основных маршрутов раздела 12, миграции, постоянные черновики, последовательную загрузку, защищённый предпросмотр, версии, идемпотентность, неизменяемую очередь, расписание, историю, очистку и диагностические endpoints. Добавлен внутренний интерфейс публикации и заблокированный адаптер по умолчанию. Только тесты подключают фиктивный адаптер.

Ожидание постоянного Donut проверяется до обычного поста: без доступного проверенного адаптера обработчик не выполняет внешних операций. Нет значения `donut_paid_duration`, подобранного предположением, нет пробных публикаций и нет автоматического открытия Donut всем.

Автоматизированные сценарии используют синтетические JPEG/PNG и фиктивные результаты VK: наборы 12/13/14 страниц; обложка и последние страницы; замены; версии; защита API; контроль файлов и квот; одновременные подтверждения; повторная галерея; частичный успех; восстановление `sending`; неизвестный результат; пауза; пропущенные слоты; будущие слоты; приоритет остатка; авторизация; очистка активной/завершённой очереди.
