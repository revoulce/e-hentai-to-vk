# Подключение публикации в VK

Целевая группа: [quetzalcoatl_cosplay](https://vk.ru/quetzalcoatl_cosplay). Адаптер реализован в `src/vk-publisher.ts`; после настройки существующая очередь публикует четыре фотографии обычного поста, затем девять других фотографий Donut от имени этого же сообщества. Расписание и подтверждение в расширении сохраняются.

## Пользовательский токен

Нужен **пользовательский** access token администратора сообщества с правами `photos` и `wall`. Токен сообщества и токен VK ID для входа не являются заменой: в [официальной схеме VK 5.199](https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json) `wall.post` принимает пользовательский токен; [загрузка и сохранение фотографий стены](https://github.com/VKCOM/vk-api-schema/blob/master/photos/methods.json) тоже используют пользовательскую авторизацию. Сервер проверяет маску прав через `account.getAppPermissions` и уровень администратора через `groups.getById`.

Используйте собственное приложение VK, которому разрешены эти методы и пользовательская авторизация. [Официальный SDK VK](https://github.com/VKCOM/vk-java-sdk#4-prepare-for-using) описывает зависимость авторизации от типа приложения. Доступность регистрации Standalone и старого Implicit Flow зависит от настроек и допуска конкретного приложения; название типа само по себе не гарантирует доступ к `wall`.

Если вашему приложению разрешён Implicit Flow, из `server/` получите ссылку:

```sh
npm run vk:auth -- <ID_ВАШЕГО_ПРИЛОЖЕНИЯ>
```

Скрипт формирует ссылку на `oauth.vk.com` для вашего app ID с `photos,wall,offline`. Откройте её в браузере, авторизуйтесь и разрешите доступ. Сохраните **только значение `access_token`** из итогового адреса в `server/secrets/vk-token.txt`. Полный адрес и токен не отправляйте в чат и не вводите в расширение. `offline` запрашивается для работы сервера, но действительность токена всё равно проверяется перед каждым слотом. Если VK отклоняет авторизацию или доступ к `wall`, сначала настройте допуск вашего приложения в кабинете VK; сторонние app ID и сервисы получения токенов не используются.

На Windows можно сохранить токен без отображения и без аргумента командной строки:

```powershell
New-Item -ItemType Directory -Force secrets | Out-Null
$vkSecret = Read-Host 'Access token VK' -AsSecureString
$vkPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($vkSecret)
try {
  [IO.File]::WriteAllText((Join-Path $PWD 'secrets/vk-token.txt'), [Runtime.InteropServices.Marshal]::PtrToStringBSTR($vkPointer))
} finally {
  [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($vkPointer)
  Remove-Variable vkSecret, vkPointer
}
```

Каталог `secrets/` исключён из Git и Docker build context. В Linux назначьте файлу права `600`, а для контейнера — владельца UID 1000. Обновление содержимого токена не требует сборки: файл читается на каждом вызове VK. После замены файла с другим inode пересоздайте контейнер для обновления монтирования.

## Постоянный Donut и закрытость фотографий

В `.env` задаются:

```dotenv
VK_GROUP_ID=quetzalcoatl_cosplay
VK_TOKEN_FILE=secrets/vk-token.txt
VK_DONUT_REFERENCE_POST=https://vk.ru/wall-<ID_ГРУППЫ>_<ID_ПОСТА>
VK_DONUT_PERMANENT_CONFIRMED_POST=-<ID_ГРУППЫ>_<ID_ПОСТА>
VK_PHOTO_PRIVACY_VERIFIED=false
```

`VK_DONUT_REFERENCE_POST` — существующая запись этой группы, настроенная в интерфейсе VK **только для донов навсегда**. Сервер читает её через `wall.getById`, проверяет владельца и `donut.is_donut: true`. Если VK возвращает `paid_duration`, он должен равняться `-1`; явно конечный срок блокирует публикацию. [Официальная документация wall.post](https://dev.vk.com/ru/method/wall.post) определяет `donut_paid_duration=-1` как постоянный доступ исключительно для донов. Новые Donut-посты всегда получают это значение, без даты открытия всем.

`paid_duration` — необязательное поле [схемы Donut](https://github.com/VKCOM/vk-api-schema/blob/master/wall/objects.json). В фактическом ответе для `-217669377_12062` оно отсутствует как при `extended=0`, так и при `extended=1`, хотя владелец подтвердил режим «навсегда». В таком случае `VK_DONUT_PERMANENT_CONFIRMED_POST` сохраняет **ID именно проверенного владельцем поста**. Этот ID должен совпадать с эталонным постом; подтверждение не переносится автоматически на другую запись и не переопределяет явно конечный срок из API. В диагностике `donutReference.durationSource` будет `owner_confirmation`; при полученном `paid_duration=-1` — `api`. Для другой записи владелец сначала проверяет её режим в интерфейсе VK. Если постоянный режим не подтверждён, публикация остаётся заблокированной.

Если проверка остановилась на Donut, поле `donutReference` показывает ID эталонного поста и прочитанные из VK `found`, `isDonut`, `paidDuration`. Причины различаются: `VK_DONUT_REFERENCE_REQUIRED` — ссылка не задана; `VK_DONUT_REFERENCE_WRONG_GROUP` — другая группа; `VK_DONUT_REFERENCE_NOT_FOUND` — запись не получена или удалена; `VK_DONUT_REFERENCE_NOT_DONUT` — ответ не подтверждает Donut; `VK_DONUT_DURATION_UNAVAILABLE` — VK не вернул срок и нет подтверждения владельца для этой записи; `VK_DONUT_NOT_PERMANENT` — явно полученный срок отличается от `-1`. При отказе авторизации `apiErrorCode` содержит только числовой код VK, без текста внешней ошибки и параметров с токеном.

По требованиям раздела 8 ТЗ нужно также проверить фактическую видимость фотографий: администратор и дон видят полный закрытый набор; обычный подписчик не видит изображения через пост, альбом стены и прямые ссылки на сохранённые фото. Для проверки способа загрузки используйте нейтральные тестовые картинки и тот же механизм `photos.getWallUploadServer` → multipart `photo` → `photos.saveWallPhoto`. Проверка обычного поста или вручную загруженного фото сама по себе не подтверждает этот механизм. Приложение не создаёт отдельный публичный альбом для Donut. Однако этот выбор API сам по себе не доказывает приватность CDN-ссылок, поэтому без завершённой проверки значение `VK_PHOTO_PRIVACY_VERIFIED` остаётся `false` и блокирует всю пару. Установите `true` только после фактической успешной проверки всех трёх ролей. При раскрытии изображений этот способ загрузки использовать нельзя.

## Проверка и запуск

Владелец фотографии и автор записи проверяются отдельно. В фактическом ответе `photos.saveWallPhoto` при `group_id=217669377` получен положительный `owner_id=381126275`. Такой ID сохраняется в строке вложения `photo381126275_<ID>` без подмены на отрицательный ID группы. Перед работой `users.get` определяет владельца используемого токена; допускаются фото этого пользователя и целевого сообщества, остальные владельцы отклоняются. `group_id` по-прежнему передаётся в обоих методах загрузки/сохранения фото.

Стена и автор самого поста задаются через `wall.post`: `owner_id=-<ID_ГРУППЫ>`, `from_group=1`, `signed=0`. После создания ответ должен подтвердить отрицательные `owner_id` и `from_id` целевого сообщества. Положительный владелец вложения не меняет эту проверку, постоянный Donut и допуск по проверенной приватности фотографий.

Для локального запуска скопируйте `.env.example` в `.env`, заполните параметры и используйте:

```sh
npm run vk:check
npm run dev:local
```

`vk:check` выполняет только чтение прав, сообщества, эталонного поста и адреса загрузки. Он не создаёт фотографии или записи. Команда возвращает `state: ready` и код выхода 0 только при прохождении всех условий. `.env` читается командами `dev`, `dev:local`, `start` и `vk:check`; токены в нём не хранятся.

В расширении откройте «Настройки» → «Публикация в VK» → **«Проверить подключение VK»**. Кнопка вызывает защищённый `POST /ehvk/api/v1/vk/check`, показывает группу и причину блокировки. После обновления токена успешная проверка снимает сохранённую блокировку авторизации; незавершённую задачу продолжите кнопкой «Продолжить» в очереди. Сама проверка не создаёт посты; обработчик передаёт готовые задачи в отложенные ВК без ожидания времени выхода.

Для Docker заполните `deploy/.env` по примеру и добавьте конфигурацию VK:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml -f deploy/compose.vk.yaml up -d --build app
docker compose --env-file deploy/.env -f deploy/compose.yaml -f deploy/compose.vk.yaml exec app node dist/src/vk-check.js
```

`VK_TOKEN_PATH` в `deploy/.env` указывает на файл хоста; Compose монтирует его как `/run/secrets/vk_token`. Основной `compose.yaml` работает и без токена VK. При последующих командах для конфигурации с VK указывайте оба `-f`.

## Сбои и повторы

После подтверждения сервер сразу готовит фотографии и создаёт два отложенных поста через `wall.post` с `publish_date` в Unix-секундах. Обычный пост выходит в выбранный слот, Donut — через минуту (18:00 / 18:01). Перед назначением читается вся очередь `wall.get(filter=postponed)`, включая добавленные вручную записи; пара резервирует обе свободные минуты. Время выбирается после загрузки файлов, чтобы длительная загрузка не сделала его просроченным. В запросе Donut по-прежнему задаётся `donut_paid_duration=-1`.

При обратном чтении проверяются также `date` и `post_type=postpone`. Подтверждённая передача имеет состояние `scheduled`; время и ID сохраняются до внешнего запроса и после его результата. ВК публикует принятые записи самостоятельно. Пауза останавливает только новую передачу; менять время или отменять уже переданные посты нужно в ВК.

Сервер последовательно ограничивает частоту вызовов VK, повторяет временные ошибки загрузки до трёх раз и сохраняет каждый полученный ID фотографии. Перед отправкой очередной пары он повторно проверяет права и постоянный Donut. Числовой ID целевой группы фиксируется в SQLite; смена группы с прежним каталогом очереди блокируется.

Каждый пост получает стабильный `guid` из сохранённого ключа операции. На одну лишь дедупликацию VK сервер не полагается. После создания он проверяет ID, автора сообщества, текст, фотографии и аудиторию через `wall.getById`. Ошибка чтения после полученного ID сохраняет ID и ссылку, но оставляет результат `unknown`; такой пост нельзя отправить повторно кнопкой «Продолжить».

При размещении фото владельца токена ВК может создать копии с отрицательным владельцем и новыми ID в сообществе. Это подтверждено для постов `-217669377_12165`, `-217669377_12166`, `-217669377_12167`: владелец, автор, тексты и назначенное время совпали, а ссылки на полноразмерные изображения оригиналов и копий оказались одинаковыми. Поэтому при изменении ID обработчик читает точные исходные фото через `photos.getById` и проверяет однозначное соответствие полноразмерных изображений по URL и размерам. Одного количества фото, одинаковых размеров или совпадения миниатюр недостаточно. Проверки стены, автора, времени и Donut сохраняются; исходные URL не записываются в журнал.

Для ранее созданных постов с `VK_POST_VERIFICATION_FAILED` после обновления сервера используйте «Сверить с ВК». Подтверждение существующего ID завершает только этот пост и позволяет передать оставшийся Donut; обычный пост не создаётся повторно.

При чтении нового Donut-поста отсутствующий `paid_duration` не вызывает ложную ошибку: постоянное значение `-1` уже передано в сохранённом запросе создания, а ответ должен подтвердить `is_donut: true`. Явно конечный срок всё равно отклоняется. Такое же правило применяется при сверке точного результата этой сохранённой операции.

«Сверить с ВК» проверяет известный ID либо ищет точное сочетание текста, автора и фотографий среди последних 1000 записей соответствующей стены, включая отдельный фильтр Donut. Найденный подходящий пост завершает этот этап без повторной отправки. Несколько совпадений, неподходящий режим Donut и отсутствие в списке оставляют результат неизвестным: неполный список, удаление и задержки VK не доказывают, что запись не была создана. Автоматической повторной отправки при таком результате нет.

Проверки кода используют фиктивные ответы VK и синтетические файлы. Действительная авторизация, допуск приложения, постоянный Donut и приватность вложений в целевой группе требуют проверки с вашим аккаунтом; без пользовательского токена они не проверены.
