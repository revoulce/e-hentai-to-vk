# Обслуживание

Каталог данных содержит `state.sqlite`, журнал WAL и `images/`. Секрет владельца хранится отдельно. Не копируйте один открытый SQLite-файл вручную. Миграции применяются при старте транзакционно; перед изменением существующей схемы создаётся SQLite-копия `state.sqlite.before-migration-*`. Эти копии также требуют внешнего хранения и контроля места.

## Резервное копирование

В этом этапе реализована согласованная **копия при остановленном сервере**. Остановка нужна для согласованности SQLite и изображений: библиотечный backup API сам согласует БД, но очистка или загрузка файлов не должны идти параллельно.

Для локального процесса завершите его через SIGTERM/SIGINT и выполните:

```sh
mkdir -p backups
DATA_DIR="$PWD/data" npm run backup -- "$PWD/backups/2026-10-08"
```

Папка назначения должна ещё не существовать и находиться вне исходного каталога данных. SQLite переносится через `node:sqlite.backup`; настройки, очередь, история и метаданные включены в эту БД. Файлы копируются отдельно, секреты не копируются.

В Docker, из корня репозитория:

```sh
mkdir -p backups
docker compose --env-file deploy/.env -f deploy/compose.yaml stop app
docker compose --env-file deploy/.env -f deploy/compose.yaml run --rm --no-deps --user 0 \
  --volume "$PWD/backups:/backup" app \
  node dist/src/backup.js /backup/2026-10-08
docker compose --env-file deploy/.env -f deploy/compose.yaml start app
```

Backup API создаёт копию SQLite с учётом WAL. Из-за root-пользователя при разовом копировании назначьте файлам копии доступ только владельцу/администратору. Храните вторую копию вне сервера. Для ежедневного запуска можно использовать systemd timer или cron на Ubuntu: остановка → backup → запуск с обработкой ошибки и ограничением количества копий. Автоматический таймер на сервере пользователя в этом этапе не установлен.

## Восстановление

1. Остановите приложение и сохраните текущий volume для возможности отката.
2. Восстановите `state.sqlite` и `images/` из одной копии в первоначальный каталог данных; для Docker это `/app/data`. Старые WAL/SHM не переносите поверх новой БД.
3. Назначьте UID/GID 1000:1000 в Docker, верните секрет отдельным защищённым файлом.
4. Запустите **один** экземпляр и проверьте readiness, очередь и наличие предпросмотров. При переносе на другой локальный путь нужно отдельно перенести серверные пути файлов в `assets` и снимках; текущий формат backup предполагает одинаковый путь данных.
5. Статус `sending` после прерывания становится `unknown`: сначала сверка с VK, затем разрешение продолжения. Никогда вручную не переводите его в `pending` без надёжной проверки отсутствия поста. Историческая копия могла не включать внешнюю публикацию, сделанную после backup: сначала сверьте VK для задач, затронутых таким откатом.

API хранит исходный снимок даже после удаления файлов по сроку: его свойства не изменяются, но `fileAvailable: false`. Повторы, частичный успех и ошибки авторизации не сокращают срок хранения активной очереди. Отмена неопределённой внешней операции запрещена.

## Журналы и ошибки

Запросы логируются без заголовков авторизации, тел, query-параметров и текстов внешних ошибок. Ответы содержат безопасный код и request ID. Docker ограничивает stdout-журналы пятью файлами по 10 МиБ. Ротация по возрасту семь дней остаётся задачей дальнейшей поставки.

- `VERSION_CONFLICT`: получить текущий черновик и показать актуальный предпросмотр.
- `DUPLICATE_IMAGE`, `FORMAT_UNSUPPORTED`, `ANIMATION_UNSUPPORTED`: заменить выбранную страницу.
- `STORAGE_QUOTA`: проверить квоту и свободный диск; активная очередь автоматически не удаляется.
- `ASSET_LOST`: требуется исправление файла и новый предпросмотр; состав принятой пары нельзя менять скрыто.
- `VK_AUTH_REQUIRED`: обновить файл пользовательского токена, затем проверить подключение в расширении или `POST /vk/check`; блокировка сохраняется после перезапуска. `/retry` сразу возобновляет передачу в отложенные ВК с будущим временем.
- `JOB_IN_VK`: пара уже передана в ВК; её время и отмена управляются в ВК. Пауза сервера не останавливает принятые ВК посты.
- `VK_SCHEDULE_EXPIRED`, `VK_SCHEDULE_FULL`, `VK_SCHEDULE_UNAVAILABLE`: временная проблема назначения времени; повторная передача выберет доступный будущий слот. Уже принятые посты не отправляются заново.
- `RESULT_UNKNOWN`: сначала `/reconcile`; повтор создания записи запрещён.
- `VK_NOT_VERIFIED` / `integration_required`: настроить VK по [vk.md](vk.md).
- `VK_POST_VERIFICATION_FAILED`: VK вернул ID, но текст, фотографии или аудитория не подтвердились. ID и ссылка сохранены; пост остаётся `unknown` и требует проверки в VK и `/reconcile`.
- `VK_REJECTED`: прочитать `posts[].last_error_details` в задаче — этап и код API относятся к конкретной операции, независимо от текущей проверки подключения. У прежних ошибок подробности могли не сохраняться.
- `VK_PHOTO_OWNER_MISMATCH`: владелец сохранённого фото отличается от целевого сообщества и пользователя текущего токена; в диагностике сохранены ожидаемый и фактический ID. Прежняя версия ошибочно отклоняла и фото владельца токена. Для таких задач обновите сервер и продолжите оставшуюся операцию. Владелец фото не определяет автора поста; ответ создания записи отдельно проверяется на авторство сообщества.
- `VK_UPLOAD_EMPTY`: загрузчик вернул пустой список фото либо пустое поле `photo`; сохранение фото не вызывается, обработчик повторяет загрузку автоматически. `VK_UPLOAD_RESPONSE_INVALID` сохраняет только типы полей ответа в `responseFields` для разбора несовместимого формата.
- `VK_HTTP_ERROR` с HTTP 502/503/504 при `photos.upload`: временный сбой загрузчика; сохранённые фотографии остаются в задаче, следующая попытка продолжает с недостающего файла. При `unknown` для создания поста по-прежнему нужна сверка, автоматическое создание заново запрещено.
- `VK_GROUP_MISMATCH`: вернуть прежнюю группу. Числовая цель сохранена в `vk_target`, чтобы вложения и остатки пары не отправлялись другому сообществу.

## Ограничения текущего этапа

Docker daemon в окружении разработки не был запущен: проверка Compose возможна, сборка и запуск контейнера — отдельная проверка. Реальные HTTPS, пользовательский VK, Donut-приватность и нагрузка 1 vCPU/2 ГБ пока не проверены. Пересоздание контейнера, резервное восстановление и измерения ресурсов на Ubuntu входят в дальнейшую приёмку.
